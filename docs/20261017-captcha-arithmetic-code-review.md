# 验证码改为算式后的登录失效代码审查与修改方案

- 审查对象：`GUIT-net-login`（本仓库）
- 审查基线：当前 `main`，`89dd7fa`（v1.0.19）
- 审查方式：只读源码、测试、配置样例、设计文档与 Git 历史
- 明确未执行：文件修改（除本报告外）、测试、程序启动、登录、注销、网络请求

## 1. 问题结论

### 1.1 直接根因

当前实现仍按“4 位字母数字字符串验证码”处理 OCR 结果。算式验证码中的运算符会在 OCR 后处理阶段被删除，随后即使 OCR 看到了算式，业务层也没有计算步骤，而是把识别文本原样作为验证码提交。

典型结果：

```text
图片：12+3
OCR 原始结果：12+3
当前 ocr_helper.classify()：过滤非字母数字后得到 123，再按长度截断
当前 portal_client/app 提交：123
服务端预期：15（或服务端规定的其他答案表示）
```

因此登录失效不是首先发生在取图、Session、ViewState 或 HTTP 表单字段层，而是发生在“识别结果规范化/业务语义转换”层。

### 1.2 失效链路

```text
GET captchaUrl
  -> PNG 校验与 captcha_epoch 递增
  -> OCR classify(png)
  -> 当前实现删除 + - * / 括号等非字母数字，并截断到 4 位
  -> 当前业务没有 parse/evaluate
  -> 原样写入 TextBoxCC
  -> POST /login 或 /logoff
  -> 门户返回“验证码错误”
  -> 现有重试再次取图，但每轮仍提交错误格式
  -> 最终转手输/失败
```

### 1.3 次要但确定存在的旧格式依赖

以下依赖不会单独解释所有失败，但在新格式下会造成输入截断、文案错误或测试失真：

- GUI 输入框最多保留 6 个字符，且粘贴时删除所有空白。算式可能含空格，空格是否有语义虽通常没有，但不应在未经规范化契约定义前直接丢弃。
- 自动识别失败时提示“请手动输入 4 位验证码”。
- OCR 接口文档规定“只保留字母数字并截断到 4 位”。
- 默认 OCR 后端的注释、`CAPTCHA_LENGTH`、测试断言都以 4 位为契约。
- 测试模拟门户只生成 4 位字母数字字符串，不能覆盖算式输入、算式答案或噪声 OCR。

## 3. 新验证码格式假设与不确定项

以下内容只根据用户描述“简单加减乘除算式”和本地代码推断，不能替代对真实图片/门户行为的确认。

### 3.1 合理默认假设

建议第一版实现只接受一个明确、安全的子集：

- 数字为十进制整数，允许多位数和前导零。
- 运算符为 `+`、`-`、`*`、`/`；图片可能显示 `×`、`÷`、全角或相似 Unicode 符号，先规范化为 ASCII `*`、`/`。
- 可有普通空格、制表符或 OCR 插入的少量空白；解析前统一忽略空白。
- 允许一元负号，例如 `-3+5`，但是否实际出现待确认。
- 括号是否出现未知；若出现，建议解析器支持成对的 `(`、`)`，并遵守标准优先级。
- 除法结果可能是整数，也可能不是整数；服务端答案格式未知，不能擅自用 Python 浮点结果直接转字符串。
- 图片噪声可能导致 `O/0`、`I/1`、`l/1`、`x/*`、`÷/`、短横线/减号等混淆；纠错必须有白名单和上下文规则，不能无条件替换所有字符。
- 算式长度可能超过 4 或 6 个字符；不能再使用固定长度截断。

### 3.2 必须向用户/服务端确认的事实

1. 算式实际字符集：是否只有 ASCII `+ - * /`，还是使用 `× ÷`、中文运算符、百分号或其他符号。
2. 是否允许括号、负数、连续运算符、前导零、小数和多步算式。
3. 除法规则：是否保证整除；若不整除，是四舍五入、向下取整、整数除法、保留小数，还是根本不会出现。
4. 提交字段 `TextBoxCC` 是否仍提交**计算答案**，还是新门户要求提交算式原文/其他字段。当前本地代码无法证明这一点。
5. 答案格式：例如 `5`、`5.0`、`05`、负数是否带 `-`、是否要求绝对值、是否大小写无关（数字答案通常无大小写问题）。
6. 登录和注销是否使用同一套算式规则。
7. 是否有真实样本图片或门户说明，以便校准 OCR 与符号映射。当前仓库的合成样本仍是旧的字母数字验证码。
8. 服务端是否在验证码错误后使 Session、表单或答案立即失效；现有代码只确认“重新取码会使旧码失效”。

## 5. 推荐实施方案

### 5.1 建议的数据类型与接口边界

建议新增 `src/captcha_math.py`，而不是让 `ocr.py` 或 `ocr_helper.py` 直接返回答案：

```text
OcrBackend.classify(png) -> OCR 原始/轻度清洗文本
captcha_math.solve(text) -> SolveResult
SolveResult.ok: bool
SolveResult.expression: str       # 规范化后的算式，不含图片噪声
SolveResult.answer: str           # 最终提交字符串
SolveResult.error_kind: str        # empty / invalid / unsupported / division / overflow
SolveResult.message: str           # 面向日志/界面的安全说明
```

`classify()` 仍负责图像识别，`solve()` 负责语言解析和数学语义，`submit()` 只负责门户通信。这样后续更换 OCR 后端不会重新实现门户逻辑。

### 5.2 OCR 文本规范化

只做有边界的规范化，不做“把任何字符猜成数字”的宽松替换：

1. 确认输入为 `str`，去除首尾空白；空串直接失败。
2. Unicode 归一化，至少把全角数字转换为半角数字。
3. 将确定的运算符别名映射：`×` -> `*`，`÷` -> `/`，全角加减乘除 -> ASCII；短横线只在上下文允许时映射为 `-`。
4. 去除普通空白；保留括号、点号、负号等后续解析所需字符。
5. 对 OCR 常见混淆仅允许上下文规则，例如数字位置上的 `O` 可候选为 `0`，运算符位置上的 `x` 可候选为 `*`；不要把包含字母的任意字符串强行修正。
6. 设置资源上限：最大表达式字符数、最大数字位数、最大括号深度、最大中间结果规模，防止异常输入消耗过大。
7. 规范化结果必须经过 tokenizer；不能仅靠正则删除未知字符后继续计算，否则会把错误 OCR 变成另一道合法算式。

### 5.3 安全算式解析与计算

禁止使用 `eval()`、`exec()`、`compile()`、动态导入或把字符串交给 shell/解释器。

推荐实现一个小型递归下降解析器，语法限定为：

```text
expression := term (('+' | '-') term)*
term       := unary (('*' | '/') unary)*
unary      := '-' unary | primary
primary    := integer | '(' expression ')'
integer    := DIGIT+
```

实现要点：

- tokenizer 只产生 `INTEGER`、`PLUS`、`MINUS`、`MUL`、`DIV`、`LPAREN`、`RPAREN`、`EOF`。
- 遵守括号和乘除优先级；拒绝相邻数字/运算符、缺失括号、空括号和多余 token。
- 使用整数算术；若除法不整除，默认返回“无法确认”而不擅自四舍五入。只有在服务端确认规则后才增加对应策略。
- 检查除数为零、负数结果、数值溢出/位数上限。
- 计算完成后按已确认契约格式化答案：默认使用无前导零的十进制字符串，负数保留 `-`。
- 解析失败、运算不支持或除法规则不明确时，不提交；转手输并刷新/保留当前图片，具体策略见下节。

### 5.4 业务流程与结果处理

建立一个共享辅助函数，例如 `solve_captcha_image(ocr, png)`，登录、注销、预取和换图全部调用：

1. `safe_available(ocr)` 为假：不自动识别，显示图片，提示手动输入结果。
2. `safe_classify(ocr, png)` 返回空串：记录 `ocr_empty`，不提交，转手输或换图。
3. OCR 返回文本：调用 `solve()`。
4. `solve()` 成功：显示规范化算式和答案中的一种明确 UI 表达，推荐输入框填最终答案；提交只传 `answer`。
5. `solve()` 失败：不把原文传给门户；日志记录失败类型，界面提示“无法解析验证码，请手动输入结果或换一张”。
6. 服务端返回 `KIND_CAPTCHA`：说明答案/图片可能错误，按现有 `maxCaptchaRetry` 换图重试。
7. 服务端返回账号密码错误、未知结果或明确网络异常：停止验证码重试，沿用现有分类。
8. 重试每轮必须 `prepare()`/`prepare_logoff()` 获取新图片，并通过现有 epoch/form generation 机制保证不提交旧图。

### 5.5 手动输入策略

推荐策略：输入框接受最终答案，允许负号和足够长度；用户不必手算第二次。若用户希望输入完整算式，也可以让 `_clean_captcha_input()` 保留运算符并在提交前调用同一 `solve()`，但必须明确 UI 文案和错误提示，避免用户输入答案却被当作算式再次计算。

建议至少支持：

- `0`、多位整数、负整数。
- 在服务端规则确认前，不接受小数答案或对非整除除法做猜测。
- 允许粘贴空格，但由统一规范化器处理；不要在 Tk 校验器中静默改变算式语义。
- 输入最大长度应高于旧的 6，具体值由服务端格式和资源上限确定，例如 64；答案和表达式分别设上限更稳妥。

### 5.6 日志与错误分类

建议使用不泄露凭据的事件名：

- `captcha_fetch_ok` / `captcha_fetch_error`
- `ocr_unavailable` / `ocr_empty` / `ocr_exception`
- `captcha_parse_invalid` / `captcha_division_unsupported` / `captcha_division_by_zero`
- `captcha_solved`：只记录表达式长度、运算符集合、答案位数；是否记录完整答案需按安全要求决定
- `captcha_submit_rejected`
- `captcha_retry`：记录当前轮次与上限
- `captcha_manual_fallback`

不要记录账号、密码、完整 PNG、完整 OCR 原文或可直接复用的验证码答案，除非明确为本地调试且有脱敏/开关。

建议新增或复用结果类别：

- `KIND_NEED_MANUAL`：OCR 不可用、识别为空或本地解析失败。
- `KIND_CAPTCHA`：已经生成合法答案并提交，但服务端拒绝验证码。
- `KIND_NETWORK`：取图/提交网络异常。
- 现有 `KIND_CREDENTIAL`、`KIND_UNKNOWN` 保持语义。

## 7. 验证方案与测试清单

### 7.1 纯解析/求值单元测试

| 类别 | 输入 | 期望 |
|---|---|---|
| 加法 | `1+2`、`12 + 3` | `3`、`15` |
| 减法 | `9-4`、`4-9` | `5`、`-5`，若负数被确认支持 |
| 乘法 | `3*4`、`3×4` | `12` |
| 除法整除 | `8/2`、`8 ÷ 2` | `4` |
| 除法非整除 | `5/2` | 按确认规则；未确认时必须拒绝，不得浮点猜测 |
| 优先级 | `2+3*4` | `14` |
| 括号 | `(2+3)*4` | `20`，仅在确认支持括号后启用 |
| 一元负号 | `-3+5`、`3*-2` | 按确认支持情况验证 |
| 空白 | ` 12 + 3 `、含制表符 | 等价于 `15` |
| 全角/别名符号 | `１２＋３`、`3×4`、`8÷2` | 规范化后得到正确答案 |
| 前导零 | `003+02` | 按契约得到 `5`，答案格式无前导零，除非服务端要求保留 |
| 非法字符 | `1a+2`、`1$2`、`hello` | 解析失败，不提交 |
| 非法结构 | `1++2`、`*2`、`2/`、`()`、`1 2` | 解析失败 |
| 括号错误 | `(1+2`、`1+2)` | 解析失败 |
| 除零 | `4/0` | 明确错误，不提交 |
| 超限 | 超长数字、过深括号、超长表达式 | 拒绝并转手输，不崩溃 |
| 注入字符 | `__import__('os')`、`1+2;...` | 解析失败，绝不执行任何代码 |

### 7.2 OCR 适配测试

- OCR 返回 `12+3`：保留 `+`，不得变成 `123`。
- OCR 返回 `12 × 3`：规范化为 `12*3`。
- OCR 返回 `8÷2`：规范化为 `8/2`。
- OCR 返回带换行、制表符、不可见字符的文本：只去除允许的空白/控制字符。
- OCR 返回 `None`、bytes、抛异常：仍由 `safe_classify()` 收敛为空串。
- OCR 返回极长字符串：不截断后继续误算，应受限拒绝。
- 图片噪声造成 `O/0`、`I/1`、`x/*`：只在上下文允许时进行有限修正；无法确认时转手输。

### 7.3 登录/注销流程测试

- 登录算式识别成功，提交计算答案，模拟门户转在线。
- 注销算式识别成功，提交计算答案，模拟门户转离线。
- 自动识别结果合法但答案错误：服务端返回 `KIND_CAPTCHA`，换新图并按上限重试。
- OCR 识别为空：不发起错误 POST，转手输。
- 算式解析失败：不发起错误 POST，转手输或换图。
- 取图网络异常：返回 `KIND_NETWORK`，不归为验证码错误。
- 提交网络异常/HTTP 错误/协议断开：返回 `KIND_NETWORK`，不重复无意义地换验证码。
- 账号密码错误：返回 `KIND_CREDENTIAL`，停止验证码重试。
- 服务端返回未知页面：保持 `KIND_UNKNOWN` 与现有状态复核语义。
- `captcha_epoch` 变化：旧输入不得提交，必须重新获取/提示用户。
- 表单代变化：旧答案不得搭配新 ViewState 提交。
- 连续超过 `maxCaptchaRetry`：进入手输，且日志包含轮次但不泄露密码/图片。
- 静默模式：成功返回 0，解析/识别失败返回 3，网络/门户失败返回 1，保持现有命令行契约。

### 7.4 兼容旧格式测试

- OCR 返回 `AB12`：兼容模式原样提交，旧模拟门户接受。
- 手动输入 `AB12`：原样提交。
- OCR 返回 `1+2`：提交 `3`，算式模拟门户接受。
- 旧字符串与新算式在同一版本中交替出现：每轮独立处理，不共享错误的长度/清洗状态。
- 旧格式含空格或小写：按既有门户大小写规则验证，不擅自改变大小写。

### 7.5 真实门户验证（需单独批准）

静态代码和本地模拟不能证明真实门户的除法、答案格式和 OCR 准确率。实施完成后，如要验证真实登录，必须先批准：请求内容、影响、回滚和预期证据；首次应使用可撤销的单次手动登录/只读取图方案，避免盲目重试导致账户或 Session 风险。

## 8. 风险与回滚

### 风险

- **服务端规则未知**：尤其是除法非整除、答案前导零、提交算式还是结果。错误假设会导致所有自动提交失败。
- **OCR 符号识别准确率下降**：ddddocr 原本针对字母数字验证码，未必能稳定识别 `+ - × ÷ / *`、括号和噪声线。
- **错误纠正误判**：把噪声误当运算符或数字可能提交另一个合法答案；必须宁可手输，不要无限猜测。
- **显示尺寸变化**：算式图片可能比旧 80x24 更宽；当前 `CAPTCHA_ZOOM = 4` 和固定窗口布局可能出现裁切或横向溢出，需要做布局验证。
- **重试放大请求量**：算式解析错误若错误地触发自动换图，可能快速消耗 Session/服务端限额；解析失败应优先手输或明确由用户换图。
- **登录与注销行为不一致**：门户可能只切换登录验证码格式，注销仍是旧格式，或反之；必须分别验证。
- **兼容分支复杂度**：同时支持旧字符串和新算式时，不能用“是否包含数字”这种模糊判断；应先尝试严格算式语法，再按旧字符串白名单回退。
- **日志泄露**：完整算式和答案可能属于短期认证秘密，日志应最小化记录。
- **打包遗漏**：新增模块若不加入显式 PyInstaller/PYZ 清单，源码可用但 exe 运行失败。

### 回滚

- 源码级回滚：恢复本次实施涉及的 `src/`、`tests/`、文档和构建清单变更；保留本报告作为审查记录。
- 行为级回滚：保留一个明确的旧字符串处理开关/兼容路径，在服务端规则未确认或 OCR 算式准确率不足时关闭自动算式提交，回退手输。
- 数据级回滚：本方案不需要修改现有 `config.json`、账号密码或系统设置；不要通过真实登录试错来验证。

## 9. 最终建议

优先级最高的修复不是替换 OCR 引擎，而是解除 `ocr_helper.classify()` 的字母数字过滤和 4 位截断，并在 OCR 与 HTTP 提交之间增加安全的算式解析/计算层。解析器必须采用白名单 tokenizer + 显式运算，禁止任何任意代码执行。登录和注销、GUI 和静默模式必须共用同一转换入口，避免四条路径行为分叉。

在用户确认服务端答案契约前，建议实现“严格解析、无法确认即手动”的保守策略，并保留旧四位字母数字字符串兼容路径。当前本地代码能够确定修复范围和直接根因，但不能单凭仓库确认除法语义、实际算式格式、答案提交格式、真实图片噪声分布和服务端是否仍允许旧验证码格式。
